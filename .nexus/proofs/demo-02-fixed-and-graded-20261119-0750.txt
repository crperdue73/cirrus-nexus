ROOT CAUSE (one code defect, measured)
  _resolve_container_digest() in backend/main.py preferred a registry digest:
      docker image inspect <img> --format '{{index .RepoDigests 0}}'
  Its docstring claimed the AEGIS images are local-only with `RepoDigests: []`.
  FALSE on this host. Docker synthesises `<repo>@<image CONFIG ID>` for never-pushed
  local images:
      aegis/frr:latest     -> aegis/frr@sha256:45659602383a...  (== .Id)
      aegis/srlinux:latest -> aegis/srlinux@sha256:e58622fb4a0c...
  So a container's "identity" came back as a CONFIG id, while the installer's pin
  (installed-image-id.txt) is a LAYER-CHAIN hash. Comparing the two always failed:
      live not in expected -> return "" -> "Could not resolve runtime digest"
  demo-01 was unaffected only because it runs NO pinned aegis/frr node, so it fell
  through to _aegis_less_identity() and attributed successfully. Any lab with an
  FRR router — i.e. all the interesting ones — was dead.

FIX (backend/main.py)
  Added _repo_digest_from_registry(): a RepoDigest is only trusted when its repo half
  actually names a registry host (contains '.', a ':' port, or is 'localhost') AND it
  is not just the image's own config id. Otherwise fall through to the layer chain.
  This restores the documented intent (identity == layer chain, comparable to the pin)
  without discarding real registry digests when they exist.

FIX (install.sh) — found while diagnosing, genuine and separate
  install.sh wrote the install record with a truncating `{ ... } > file` of exactly
  THREE keys, never `installed_substrate_digests`, while _pinned_substrate_digests()
  reads that key. Moved record-writing to a new Step 7e that runs AFTER Step 7d builds
  aegis/srlinux, and emits all four keys with both substrate chains.
  HONESTY NOTE: this was NOT what fixed demo-02. The RepoDigest fix was. The srlinux
  chain is not counted as a substrate node (no 'aegis/frr' tag, no frr label), so it
  never entered the identity set. Step 7e is a real consistency repair, not the cure.
