# API reference

AEGIS exposes **11 routes** on one FastAPI app (`backend/main.py`). This page is a reader's
reference to them; the app also generates its own documentation from the same route table at
`/docs` (Swagger UI), `/redoc` and `/openapi.json`, so nothing here can drift silently — if this page
and `/openapi.json` disagree, the running app is right and this page is a bug.

Everything below was read out of the tree, not written from memory: the route list, the parameter
lists and their `in`/`required` flags come from the app's own OpenAPI document
(`main.app.openapi()`, generated by importing `backend/main.py`), and the response shapes come from
the handler bodies.

Base URL: `http://<host>:8000`. Bind address and port are overridable with `AEGIS_HOST` /
`AEGIS_PORT` (default `0.0.0.0:8000`); a bad `AEGIS_PORT` exits with a sentence naming the problem,
not a traceback.

## Summary

| Method | Route | Parameters | Purpose |
|--------|-------|------------|---------|
| `GET` | `/api` | — | service card |
| `GET` | `/api/labs` | — | the served lab catalog |
| `GET` | `/api/labs/{lab_id}` | `lab_id` (path) | one lab's definition |
| `GET` | `/api/labs/{lab_id}/guide` | `lab_id` (path) | the lab's Markdown student guide (served raw) |
| `GET` | `/api/labs/{lab_id}/topology` | `lab_id` (path) | the lab's rendered topology diagram |
| `POST` | `/api/labs/reload` | — | re-read lab definitions and clear the grader cache |
| `POST` | `/api/sessions/start` | `lab_id` (query, required), `student_name` (query, default `Student`) | deploy a lab and open a session |
| `GET` | `/api/sessions` | — | running sessions, newest first |
| `GET` | `/api/sessions/{session_id}` | `session_id` (path) | one session's status (used by *Reconnect*) |
| `POST` | `/api/sessions/{session_id}/submit` | `node` (query, required) | grade one node |
| `POST` | `/api/sessions/{session_id}/stop` | — | tear down a session |

**No route takes a request body.** Every input is a path or query parameter — that is why the
examples below are plain `curl` URLs with no `-d`. The shipped UI calls the API exactly this way
(`frontend/index.html`: `fetch('/api/sessions/start?lab_id=…')`, `…/submit?node=…`), and the app's
OpenAPI document reports `requestBody` for **zero** operations.

---

## The two parameters people get wrong

- **`lab_id` is the lab's directory-style id, not its title.** The ids are long:
  `demo-01-two-pcs-and-a-real-switch-unsolved`, `demo-02-two-switches-one-router-unsolved`. Get them
  from `GET /api/labs` rather than typing them.
- **`node` is one name from the session's own node list**, e.g. `sw1`, `sw2`, `r1`, `pc-a`. A node
  the lab does not have is a **`409` refusal** whose detail carries the node list — the request was
  understood, the answer is "that node isn't here" (see *Status codes*).

## Routes in detail

### `GET /api` — service card

```json
{"service": "NEXUS", "version": "0.3.0", "labs_count": 2}
```

`labs_count` is the number currently loaded, so it moves if a lab definition is refused at load
time. `version` is the **API's own** version string, not the release tag — see
[Release status](../README.md#release-status).

### `GET /api/labs` — the catalog

```json
{"labs": [ … ]}
```

One entry per lab definition the loader accepted, using the `LabDef` model (`backend/main.py`).
Definitions are read **once at startup** and cached: editing a YAML or a grader changes nothing
until `POST /api/labs/reload`.

### `GET /api/labs/{lab_id}` — one definition

The same object the catalog carries. Unknown id → `404`.

### `GET /api/labs/{lab_id}/guide` — the student guide

The lab's Markdown guide, served **raw** (`Content-Type: text/markdown`) from the resolver the
lab's own `guide:` field points at. A lab with no guide returns `404`. Browsers render
`text/markdown` inconsistently — Firefox displays it, Chrome and Safari typically download it. The
app ships no Markdown renderer; the **Lab Guide** button is a `window.open()`.

### `GET /api/labs/{lab_id}/topology` — the topology diagram

A rendered diagram for the lab, generated from the lab's YAML on request. This is what the
**Topology** button opens.

### `POST /api/labs/reload` — re-read definitions

```json
{"status": "reloaded", "count": 2}
```

If a definition is refused, the status becomes `"reloaded with skips"` and a `skipped` key names the
definition and the reason, instead of one bare `500` for the whole reload. Also clears the grader
cache, so an edited grader takes effect here.

### `POST /api/sessions/start?lab_id=…&student_name=…`

Deploys the lab with containerlab and opens a session. `lab_id` is required; `student_name`
defaults to `Student`. The response carries the `session_id` and a per-node `ttyd` URL — one
terminal per container, on a port allocated from **8765–9765**.

Deploy is serialized (concurrent starts queue) and its failure modes are separated on purpose:
an unknown lab is `404`, a **failed deploy is `500`** — a start that could not complete never
reports a session it does not have. A start can also be refused with `409` (a `CapabilityRefusal`: the
system will not deploy a lab it cannot later attribute) and in both failure paths the containers the
attempt already created are torn down rather than leaked.

### `GET /api/sessions` — live sessions

Newest first. Each entry carries the session's `runtime_digest` (the identity a grade is taken
against; may be `""` only mid-teardown) and the substrate image the lab was pinned to.

### `GET /api/sessions/{session_id}` — one session

Returns `session_id`, `lab_id`, `student_name`, `status`, `created_at`, `nodes` (the node-name
list), `status_updated_at`, `last_graded_node`, and **both digests**:

| field | meaning |
|-------|---------|
| `runtime_digest` | the digest pinned at session start |
| `runtime_digest_live` | the digest computed from the containers running now |
| `runtime_digest_matches` | `true` only if the two agree |

`runtime_digest_matches: false` means the substrate moved under a live session. Grades taken
against it are refused rather than reported as passes or failures — see
[GRADING-MODEL.md](GRADING-MODEL.md).

### `POST /api/sessions/{session_id}/submit?node=…` — grade one node

```json
{"session_id": "…", "node": "sw1", "grade": { … }}
```

`grade` carries `passed`, `score`, `feedback`, `competencies`, the in-band `status`
(`graded` / `error` / `refused`) and the `runtime_digest` it was taken against.

### `POST /api/sessions/{session_id}/stop` — tear down

Destroys the containers and frees their `ttyd` ports. Teardown runs inside the same deploy lock as
`start`, because `start` allocates ports inside that lock — unlocked, a start could hand out a port
a stop was about to release.

## Status codes

| code | when |
|------|------|
| `200` | the request was answered truthfully |
| `404` | unknown lab, or a session record that does not exist (`GET`/`submit`/`stop` on an unknown session id) |
| `409` | **refusal**: the system could not make a truthful statement (node down, substrate changed since start, no grader, or a node the lab does not have) — never a silent pass |
| `422` | a required query parameter is missing (`lab_id` on `start`, `node` on `submit`) — FastAPI validation, returned before the handler runs |
| `500` | a deploy failed, **or** a teardown could not complete |

The `409` distinction is the point of the grading model: *"nobody looked"* must never be rendered as
*"wrong"*. A refusal's reason is the string in `detail`.

A node the lab does not have is a `409`, **not** a `404`: the request was understood, and the answer is
"that node isn't here" (`detail` carries the node list). A `404` means the lab or the session record
itself does not exist.

A failed `stop` is `500` and is **retryable**: the session stays listed until the lab is really gone, so
the same `stop` call can be issued again. That is deliberate — reporting `destroyed` while containers
still run is the one outcome teardown must never produce.

## Three-call walkthrough

```bash
# 1. deploy a lab — the response carries session_id and per-node ttyd URLs
curl -X POST 'http://localhost:8000/api/sessions/start?lab_id=demo-01-two-pcs-and-a-real-switch-unsolved&student_name=Ada'

# 2. grade one node
curl -X POST 'http://localhost:8000/api/sessions/<session_id>/submit?node=sw1'

# 3. tear it down
curl -X POST 'http://localhost:8000/api/sessions/<session_id>/stop'
```

These are the same three calls the UI makes.

## Exposure

**The API has no authentication.** Not on the routes above, not on `/docs`, and not on the `ttyd`
terminals (`8765`–`9765`) either — those are separate processes bound to all interfaces. The server
also binds `0.0.0.0` by default. On a classroom subnet that is usually the intent; on a shared or
untrusted network it is not. `AEGIS_HOST=127.0.0.1` plus your own reverse proxy and auth is the
supported shape if you need one. See the Security section of
[`../SECURITY.md`](../SECURITY.md) and [`OPERATIONS.md`](OPERATIONS.md).

## Re-checking this page

The route table, the parameter lists and the "no request bodies" claim are all machine-checkable
against the tree — no server, no containers needed:

```bash
python3 -m pip install -r requirements.txt   # fastapi, uvicorn, pyyaml
python3 - <<'PY'
import sys; sys.path.insert(0, "backend")
import main
for path, ops in sorted(main.app.openapi()["paths"].items()):
    for method, op in ops.items():
        params = [(q["name"], q.get("required", False), q["in"]) for q in op.get("parameters", [])]
        body = "BODY" if "requestBody" in op else "no-body"
        print(method.upper(), path, params, body)
PY
```

That prints the same 11 rows as the summary table above. If a row disagrees, this page is stale:
fix the page, not the printout.
